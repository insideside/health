# Сервер «Тренера» на белом IP: требования по числу пользователей

Документ описывает, какое железо и настройки нужны, чтобы «Тренер» работал из интернета по белому IP
для 10-100 человек. Все оценки ориентировочные. Их стоит проверить нагрузочным тестом на выбранной машине (см. конец документа).

## Что на самом деле нагружает сервер

| Часть | Нагрузка | Вывод |
|---|---|---|
| Веб и синк (FastAPI, uvicorn) | При открытом приложении `GET /api/sync/head` раз в 10 с, в фоне раз в 60 с; полный обмен только при изменениях. 100 человек дают ≈ 5-10 запросов/с в пике | Хватит 1-2 ядер любого современного процессора |
| База (SQLite, WAL) | ≈ 30-80 записей на человека в день, ≈ 10-30 МБ на человека в год с историей правок | 100 человек за год дают 1-3 ГБ. SQLite справляется: записи короткие |
| Статика и PWA | Оболочка ≈ 1-2 МБ, кэшируется на устройстве и заново качается только при обновлении | Канал почти не нагружается |
| **Локальная ИИ (Ollama, qwen3:30b)** | Разбор еды, чат, рацион, рецепты, недельный разбор, программы. Модель занимает ≈ 19 ГБ, задачи с `think` идут 20-90 с | **Главный ресурс. Размер сервера определяет именно она** |

Потребность в ИИ на одного активного человека в день (режим «по кнопке»):
≈ 2-4 разбора еды (многое уже решают справочник и память тренера), 2-5 сообщений в чат, раз в неделю разбор недели
и изредка программа или рацион. Это ≈ 6-10 задач и 8-15 тыс. сгенерированных токенов в день.
Около трети приходится на вечерний пик (19:00-23:00).

| Пользователей | Токенов в пиковый час | Нужная скорость ИИ | Задач одновременно в пике |
|---|---|---|---|
| до 10 | ≈ 15-25 тыс. | ≈ 5-7 ток/с | 1-2 |
| 10-20 | ≈ 30-50 тыс. | ≈ 10-15 ток/с | 2-3 |
| 20-30 | ≈ 50-75 тыс. | ≈ 15-20 ток/с | 3-4 |
| 30-50 | ≈ 75-125 тыс. | ≈ 20-35 ток/с | 4-8 |
| 50-100 | ≈ 125-250 тыс. | ≈ 35-70 ток/с | 8-16 |

Средней скорости мало: важно ещё, **сколько ждёт человек, чья задача стоит пятой в очереди**. Отсюда главное требование.
Начиная с ≈ 20 пользователей задачи ИИ должны выполняться параллельно: несколько потоков в Ollama или vLLM
с непрерывным батчингом (continuous batching). Иначе в вечерний пик ответ чата будет идти минутами.

Примерная скорость qwen3:30b (MoE, ≈ 3 млрд активных параметров, квантизация Q4) в одном потоке:
Mac mini M4 Pro ≈ 60-80 ток/с, Mac Studio M4 Max ≈ 90-110, M3 Ultra ≈ 100-130,
RTX 3090/4090 ≈ 130-190, RTX 5090 ≈ 200-250. Параллельные потоки дают больше токенов в сумме.
На Mac прирост скромный (≈ 1,5-2× на 4 потоках). На NVIDIA с vLLM он в разы больше: сотни и больше тысячи ток/с суммарно.

## Конфигурации

Память под ИИ: модель ≈ 19 ГБ плюс контекст ≈ 1,5 ГБ на каждый параллельный поток (контекст 16 тыс. токенов).
На Mac память общая с системой, поэтому к этому прибавляется ≈ 8-12 ГБ на macOS и приложение.

### До 10 пользователей

| | macOS | Linux / Windows |
|---|---|---|
| Машина | Mac mini M4 Pro, **48 ГБ**; минимум: M4 или M4 Pro 32 ГБ | ПК: 6-8 ядер, 32 ГБ ОЗУ, **GPU 24 ГБ** (RTX 3090 / 4090); минимум: 16 ГБ GPU (RTX 4060 Ti 16 / 4070 Ti Super), часть слоёв уйдёт в ОЗУ, скорость ≈ 25-40 ток/с |
| Диск | SSD 256 ГБ (модель ≈ 19 ГБ, база < 1 ГБ, бэкапы) | NVMe 500 ГБ |
| ИИ | Ollama, 1 поток (как сейчас) | Ollama, 1-2 потока |
| Потребление | ≈ 5-10 Вт в простое, ≈ 50-70 Вт под ИИ | ≈ 60-100 Вт в простое, 350-500 Вт под ИИ |
| Канал | от 10 Мбит/с отдачи | от 10 Мбит/с отдачи |

### 10-20 пользователей

| | macOS | Linux / Windows |
|---|---|---|
| Машина | Mac mini M4 Pro **64 ГБ** (48 ГБ хватит на 2 потока) | 8 ядер, 32-64 ГБ ОЗУ, **GPU 24 ГБ** (RTX 3090 / 4090) |
| Диск | SSD 512 ГБ | NVMe 500 ГБ-1 ТБ |
| ИИ | Ollama, `OLLAMA_NUM_PARALLEL=2`, 2 обработчика задач в приложении | Ollama, 2-3 потока |
| Канал | от 20 Мбит/с отдачи | от 20 Мбит/с отдачи |

### 20-30 пользователей

| | macOS | Linux / Windows |
|---|---|---|
| Машина | **Mac Studio M4 Max, 64 ГБ** (пропускная способность памяти вдвое выше, чем у M4 Pro) | 8-12 ядер, 64 ГБ ОЗУ, **RTX 4090 24 ГБ или RTX 5090 32 ГБ** |
| Диск | SSD 1 ТБ | NVMe 1 ТБ |
| ИИ | Ollama, 3-4 потока | Ollama (3-4 потока) или vLLM |
| Питание | ИБП на ≈ 10 минут | ИБП на 1000-1500 ВА |
| Канал | от 30 Мбит/с отдачи | от 30 Мбит/с отдачи |

### 30-50 пользователей

| | macOS | Linux (Windows не рекомендуется: vLLM на нём работает только через WSL2) |
|---|---|---|
| Машина | Mac Studio **M4 Max 128 ГБ** или **M3 Ultra 96 ГБ**. В пик ответы уже будут ждать в очереди: Mac держит параллельные запросы заметно хуже NVIDIA | 12-16 ядер, 64-128 ГБ ОЗУ, **RTX 5090 32 ГБ** или **2 × RTX 3090/4090** |
| Диск | SSD 1 ТБ | NVMe 1-2 ТБ |
| ИИ | Ollama, 4-6 потоков | **vLLM** (непрерывный батчинг), 8+ потоков |
| Канал | от 50 Мбит/с отдачи | от 50 Мбит/с отдачи |

### 50-100 пользователей

| | macOS | Linux |
|---|---|---|
| Машина | **Не рекомендуется** как единственный сервер ИИ: даже M3 Ultra не даст приемлемого ожидания в вечерний пик. Вариант: Mac для приложения и базы плюс отдельный Linux-сервер с GPU для ИИ в локальной сети | 16+ ядер, 128 ГБ ОЗУ, **RTX PRO 6000 (96 ГБ)** или **2 × RTX 5090**; либо два сервера ИИ за очередью |
| Диск | - | NVMe 2 ТБ, второй диск или NAS под бэкапы |
| ИИ | - | vLLM, 16+ потоков; при желании модель покрупнее или вторая модель для быстрых задач (разбор еды) |
| Питание, охлаждение | - | ИБП 1500-2200 ВА, 600-1200 Вт под нагрузкой, продуманное охлаждение и шум |
| Канал | - | от 100 Мбит/с отдачи |

Если сервер ИИ стоит отдельно, приложение обращается к нему по локальной сети. Сейчас это запрещено
намеренно (`OLLAMA_URL` только loopback, см. «Что поменять в приложении»).

## Обязательно для белого IP (при любом числе пользователей)

1. **Домен и настоящий сертификат.** Самоподписанный сертификат с установкой профиля годится для своей сети,
   но не для чужих людей. Нужен домен (или DDNS, если IP не статический) и Let's Encrypt.
   Проще всего поставить впереди **Caddy** (сам получает и продлевает сертификат) и проксировать на `127.0.0.1:8791`.
2. **Наружу открыты только 443 (и 80 для получения сертификата).** Порты 8790/8791 и Ollama 11434 наружу закрыты.
   Ollama и сейчас принимает только 127.0.0.1, так и оставить.
3. Файрвол (ufw / pf / брандмауэр Windows), автоматические обновления ОС, вход по SSH только по ключу.
4. Fail2ban или аналог на повторные неудачные входы (в приложении ограничение попыток уже есть, 10 в окно).
5. **Бэкапы вне сервера:** ежедневная копия базы (`sqlite3 .backup` или встроенный бэкап) на другой диск или в облако
   с шифрованием. Проверка восстановления раз в месяц.
6. ИБП и автозапуск после сбоя питания (launchd / systemd / служба Windows).
7. Мониторинг: доступность снаружи, свободное место на диске, длина очереди ИИ, температура GPU.
8. Юридическое. Приложение хранит данные о здоровье (вес, сон, цикл, лекарства). Для чужих людей нужны
   согласие на обработку и понятная политика (есть основа: [PRIVACY.md](PRIVACY.md)), а по российскому праву
   ещё и требования 152-ФЗ к персональным данным.

## Что поменять в приложении для > 4 пользователей

| Что | Сейчас | Нужно |
|---|---|---|
| Регистрация | `MAX_USERS = 4`, открытая, пока есть место | Лимит из настройки, **регистрация по приглашениям** (код от администратора) |
| Пары | Партнёр видит прогресс партнёра, все остальные тоже «свои» | Явные связи «пара/группа» с согласием обеих сторон |
| Очередь ИИ | Один обработчик, задачи строго по одной | N обработчиков (по числу потоков модели), справедливая очередь (не больше 1-2 задач одного человека одновременно), лимит задач в день на человека |
| Сервер ИИ | Только 127.0.0.1 | Разрешить адрес в локальной сети или vLLM (OpenAI-совместимый API) через явную настройку |
| Администрирование | Нет | Страница администратора: пользователи, сброс пароля, очередь ИИ, место на диске |
| База | SQLite | До 100 человек SQLite достаточно (WAL, одна машина). Postgres нужен, только если приложение будет на нескольких серверах |
| Сессии и устройства | Токены устройств с очисткой через 60 дней | Так и оставить, плюс выход со всех устройств из админки |
| Погода | Запросы к Open-Meteo с сервера | Кэш по городу на 30-60 минут (с ростом числа людей важен лимит запросов) |

## Как проверить выбранную машину

1. Поднять тестовый экземпляр (`TRAINER_DATA=... uv run run.py`) и завести N тестовых пользователей.
2. Скриптом эмулировать вечерний пик: каждый «пользователь» опрашивает `/api/sync/head` раз в 10 с,
   пишет 3-5 записей и отправляет 1-2 задачи ИИ (чат, разбор еды) за 15 минут.
3. Смотреть: время ответа синка (цель < 200 мс), **время ожидания задачи ИИ в 95 % случаев** (цель: чат < 60 с,
   еда < 30 с), загрузку GPU и памяти, температуру.
4. Если ожидание ИИ выше цели, добавить потоков или перейти на следующую ступень. Веб-часть почти наверняка
   будет в запасе.
